# Безопасная корректировка финансовых платежей

Статус: проектирование, не реализовано. Документ не меняет схему и не разрешает автоматическое исправление существующих записей.

## Задача

Исправлять ошибочно зарегистрированные платежи, не редактируя и не удаляя исходные строки ledger. Корректировка должна быть отдельным подтверждённым событием с причиной, автором (user_id), датой и ссылкой на исходный платёж.

Корректировка означает, что исходная запись была внесена ошибочно или должна быть заменена. Она не означает возврат денег от кредитора/поставщика на банковский счёт. Реальный возврат денег — отдельное поступление, а не отмена исторического платежа.

## Что нельзя делать

- Не UPDATE/DELETE строк debt_payments, obligation_payments или irregular_expense_payments.
- Не менять баланс долга напрямую из API в обход ledger.
- Не восстанавливать обязательство простым присваиванием старой даты, если после исходного платежа уже были другие оплаты.
- Не удалять автоматически expense, созданный оплатой нерегулярного расхода: его связь с payment должна остаться прослеживаемой.
- Не исправлять legacy-строки с expense_id NULL по совпадению суммы/даты без однозначного доказательства.
- Не считать запись в двух таблицах двумя денежными расходами: irregular payment и связанный expense — один факт.

## Общие требования к модели

1. Отдельная append-only запись отмены/корректировки с уникальным request_id и уникальностью по исходному платежу (одна отмена на исходную запись).
2. Сохраняются исходный payment_id, user_id, сумма, дата, bucket_id, причина и created_at.
3. API проверяет принадлежность исходного платежа пользователю и идемпотентность запроса.
4. Вставка отмены и все производные изменения выполняются атомарно на стороне D1 (триггеры и/или DB.batch).
5. Повтор запроса возвращает уже созданную отмену, не применяя эффект второй раз.
6. Нельзя отменить отмену или отменить уже отменённый платёж без отдельного сценария повторного исправления.
7. Все денежные агрегаты используют net amount = исходные платежи минус отмены. Сырые исходные строки остаются доступными в истории.
8. UI показывает исходный платёж и связанную отмену рядом, включая причину. История не должна выглядеть так, будто исходной оплаты никогда не было.

## Долги — первый кандидат

Предлагаемая таблица `debt_payment_reversals`:
- id, user_id, debt_payment_id (уникальный), amount, reversed_on, reason, request_id, created_at.
- FK/триггеры подтверждают, что debt_payment_id принадлежит тому же user_id и amount равен исходной сумме.
- AFTER INSERT триггер возвращает сумму в `debts.balance` и переводит статус в open при положительном остатке.
- Перед вставкой проверяется, что исходный платёж ещё не отменён.

Обязательная синхронизация агрегатов:
- bucket available: allocations − expenses − debt payments + debt reversals − obligation payments;
- финансовая сводка за месяц: debt payments − debt reversals;
- прогноз минимального платежа: net paid this month, а не gross payments;
- отчёт аудита долга: initial_amount − net payments; результат остаётся диагностическим, потому что баланс мог меняться по другим легитимным причинам (начисления, ручные корректировки, миграция).

Проверки:
- частичная оплата долга и полное закрытие, затем отмена и восстановление статуса;
- отмена не создаёт второй возврат при повторном request_id;
- второй request_id для уже отменённого платежа отклоняется;
- отмена возвращает деньги только в исходную корзину, включая архивную корзину как историческую ссылку;
- конкурентные запросы не могут отменить одну запись дважды;
- все SQL bucket guards, API summary, forecast и read-only audit учитывают reversal ledger.

## Обязательства — отдельная, более сложная модель

Сейчас `payment_obligations.due_date` является изменяемым курсором графика, а `obligation_payments.scheduled_due_date` фиксирует оплаченное вхождение. Есть уникальный индекс по (obligation_id, scheduled_due_date). Простая отмена только вернёт деньги, но не освободит вхождение для повторной оплаты и не восстановит корректно график.

До реализации нужно:
1. Ввести append-only журнал событий графика/вхождений либо отдельную таблицу occurrence claims с состояниями paid/reversed.
2. Перенести проверку уникальности вхождения с текущего безусловного уникального индекса на атомарную проверку активного состояния в триггере/транзакции.
3. Сохранить возможность повторно оплатить отменённое вхождение, не удаляя исходный payment.
4. Определить поведение при отмене не последнего платежа, когда после него уже оплачены следующие вхождения.
5. Восстанавливать ближайшее неоплаченное вхождение по журналу, а не слепо откатывать `due_date`.
6. Для разовых обязательств корректно восстанавливать active-состояние только если оно не было изменено пользователем позднее.

До выполнения этих условий отмена платежа обязательства не должна быть доступна.

## Нерегулярные расходы — отдельная модель

Одна оплата создаёт expense в `expenses`, payment row в `irregular_expense_payments` и сдвигает `irregular_expenses.next_date/active`. Поэтому нужны:
- отдельный reversal ledger для оплаты;
- явная связь с созданным expense_id (только если она существует и подтверждена);
- корректировка bucket-агрегатов через net payment/expense semantics без двойного возврата;
- восстановление расписания только на основании событий после исходной оплаты;
- возможность повторно оплатить отменённый scheduled occurrence (сейчас его уникальный индекс блокирует повтор);
- защита от удаления связанного expense и сохранение исходной пары payment/expense в истории.

Legacy-платежи без expense_id не должны автоматически отменяться через удаление похожего expense. Сначала требуется ручная идентификация.

## Этапы реализации

1. **Долги:** миграция reversal ledger, DB-триггеры, API action, отображение истории, обновление всех агрегатов, тесты конкурентности и идемпотентности.
2. **Обязательства:** журнал occurrence событий и переход от уникального индекса к проверке активного вхождения, затем API/UI отмены и тесты последовательности нескольких оплат.
3. **Нерегулярные расходы:** связанная отмена payment + expense + расписания, включая legacy-случаи и тесты отсутствующей/неоднозначной связи.
4. Только после тестов — отдельная read-only сверка реальной D1 и контролируемая ручная обработка конкретных подтверждённых случаев.

## Критерии готовности

- Все исходные платежи остаются неизменными.
- Каждая отмена имеет причину и ровно одну ссылку на исходный платёж.
- Повторные запросы безопасны.
- Балансы, корзины, месячная сводка, прогноз и история показывают согласованные net amounts.
- Тесты доказывают сценарии до/после отмены, повторной оплаты и конкурентного запроса.
- Ни один исторический платеж не исправляется массово или автоматически на основании эвристического совпадения.
